# Handlungsplan zum Deep Review vom 2026-09-30

Basis: Deep Review von `dborgards/eds-dcf-net @ 86e7295` (v1.14.0), abgelegt
unter [`docs/reviews/2026-09-30-deep-review.md`](reviews/2026-09-30-deep-review.md).
Die Befund-IDs (S7, X7, L3, CI-1, …) verweisen auf dieses Dokument; der Plan ist
so formuliert, dass ein Subagent ein Arbeitspaket auch **ohne** das Review
bearbeiten kann.

Status-Legende: `[ ]` offen · `[~]` in Arbeit · `[R]` PR offen · `[x]` gemergt · `[-]` zurückgestellt

## 0. Arbeitsweise und Tracking

- **Kein Issue pro Befund.** Dieser Plan ist das Arbeitsdokument. Es wird genau
  **ein** Tracking-Issue angelegt (`Deep Review 2026-09-30 – Umsetzungsplan`),
  das auf diese Datei verlinkt und die WP-Liste als Checkliste spiegelt. Jede PR
  referenziert es mit `Refs #<n>` (nicht `Closes`), damit die PR-Beschreibung
  einen stabilen Anker hat und der Release-Notes-Generator nichts Falsches
  schließt.
- **Eigene Issues nur für zurückgestellte Themen** (Abschnitt 6), weil sie
  über diesen Plan hinaus überleben müssen und diskutiert werden sollen.
- **Statuspflege:** Der Orchestrator (Hauptsession) aktualisiert die Status-
  Spalten in Abschnitt 7 gesammelt pro Welle in einer `chore(docs):`-PR.
  Subagents ändern diese Datei **nicht**, um Merge-Konflikte zwischen parallelen
  Branches zu vermeiden.
- **Ablauf pro Arbeitspaket (WP):** Subagent in eigenem Worktree → Branch von
  aktuellem `develop` → Repro-Test (rot) → Fix → Tests grün → PR nach `develop`
  → Bericht an Orchestrator → User merged (regulärer Merge-Commit).

## 1. Verbindliche Regeln für jeden Subagent

Diese Regeln gehen in jeden Agent-Prompt (siehe Vorlage in Abschnitt 5).

1. **Branching** (CLAUDE.md): nie direkt auf `main`/`develop`; Branch
   `fix/…`, `feat/…`, `refactor/…`, `chore/…`, `ci/…`; PR gegen `develop`;
   ein Anliegen pro PR; **keine `Co-Authored-By`-Zeilen** im Commit.
2. **Commit-Konvention** (`.github/copilot-instructions.md` § Commit
   Convention): `fix(scope):` für Verhaltenskorrekturen, `feat(scope):` für
   neue öffentliche API, `chore`/`docs`/`ci`/`refactor`/`test` ohne Release-
   Wirkung. Kein `!` und kein `BREAKING CHANGE:`-Footer ohne ausdrückliche
   Freigabe in Abschnitt 3. Maßgeblich ist der **PR-Titel**, weil Feature-PRs
   nach `develop` als ein Commit landen. Präzisierung:
   - Fügt ein PR **neue öffentliche Member** hinzu (Property auf einem
     Modell, Option, Methode), ist der Typ `feat`, auch wenn der Anlass ein
     Bugfix ist: neue API bedeutet Minor-Release und gehört in die
     Release-Notes.
   - Neue Konstanten in `ParseDiagnosticCodes` oder neue Validation-Issue-
     Codes, die einen Fix begleiten, bleiben `fix` (Präzedenz: #568).
   - `chore` ist laut Konvention Änderungen vorbehalten, die weder `src`
     noch Tests berühren. Verhaltensneutrale Änderungen in `src` sind
     `refactor`.
3. **Repro zuerst.** Jeder Fix beginnt mit einem fehlschlagenden Test, der den
   Befund exakt reproduziert (Namensschema `MethodName_Scenario_ExpectedBehavior`,
   AAA, XUnit + AwesomeAssertions). Erst dann der Fix.
4. **Boundary-&-Regression-Matrix** aus `CONTRIBUTING.md` § "Boundary &
   regression test guide" ausfüllen und in die PR-Beschreibung (Template
   `.github/PULL_REQUEST_TEMPLATE.md`) übernehmen, sobald Parser, Writer,
   Validator oder Converter berührt werden.
5. **Öffentliche API nur additiv.** Keine Entfernung/Umbenennung/Typänderung
   öffentlicher Member oder Parameternamen. Vor der PR
   `tools/apicompat-check.sh` ausführen. Neue öffentliche Member brauchen XML-
   Doku (`TreatWarningsAsErrors`). Checkliste `CONTRIBUTING.md` § "Public API
   compatibility checklist" abhaken.
6. **Zwei Zielframeworks:** `netstandard2.0` und `net10.0`. Keine neuen
   Paketabhängigkeiten in `src/EdsDcfNet` (Polyfill 11.4.0 ist vorhanden).
   Kein `Encoding.GetEncoding(1252)` ohne CodePages-Provider – nicht
   verfügbar, siehe WP-31.
7. **Kultur:** ausschließlich `CultureInfo.InvariantCulture` für Parse/Format;
   keine String-Interpolation für Zahlen in Datei-Ausgaben.
8. **Build & Test** (macOS/Linux; der net48-Host ist nur unter Windows
   ausführbar, deshalb wie in `CONTRIBUTING.md` vorgeschrieben mit `-f net10.0`
   testen; der Build kompiliert trotzdem beide Zielframeworks):

   ```bash
   dotnet build -c Release
   dotnet test tests/EdsDcfNet.Tests -c Release --no-build -f net10.0
   ```

   Voraussetzung ist ein SDK aus dem Band 10.0.4xx (`global.json`, siehe V3).

   Corpus-Snapshots (`tests/EdsDcfNet.Tests/Integration/Corpus*`) nur mit
   `UPDATE_CORPUS_SNAPSHOTS=1` erneuern und **jede** Snapshot-Änderung in der
   PR-Beschreibung erklären.
9. **Kein Scope-Creep.** Wer außerhalb seines WP einen Fehler findet, meldet
   ihn im Abschlussbericht, fixt ihn aber nicht.
10. **Konfliktträchtige Dateien** (nur ein WP zur Zeit darf sie ändern; der
    Orchestrator serialisiert, siehe Abschnitt 4):
    `Parsers/CanOpenReaderBase.cs`, `Parsers/CanOpenSectionParsers.cs`,
    `Parsers/IniParser.cs`, `Writers/IniWriterBase.cs`,
    `Validation/CanOpenModelValidator.cs`, `Parsers/XddCommNetProfileParser.cs`,
    `Parsers/SecureXmlParser.cs`, `Writers/XddProfileBuilder.cs`,
    `Writers/XddApplicationProcessBuilder.cs`, `Writers/XddWriter.cs`,
    `tools/semantic-release-run.sh`, `README.md`.
11. **XSD schlägt Plantext.** Für alle Strukturfragen zu XDD/XDC ist das
    Schema unter `tests/EdsDcfNet.Tests/Fixtures/Schemas/cia-311/` maßgeblich.
    Widerspricht eine Aussage in diesem Plan oder im Review dem Schema, gilt
    das Schema; der Agent meldet den Widerspruch im Abschlussbericht. (Anlass:
    die Namespace-Regel in WP-17 war zweimal falsch formuliert, bevor sie am
    Schema geprüft wurde.)
12. **Abschlussbericht** (an den Orchestrator, nicht an den User): PR-URL,
    Commit-Liste, geänderte öffentliche API (oder "keine"), Snapshot-Diffs,
    ausgefüllte Matrix, offene Fragen, Befunde außerhalb des Scopes.
13. **Rohablagen dürfen nicht veralten.** Wo ein WP neben einem bestehenden,
    normalisierten Property eine formatspezifische Rohablage einführt
    (`fileVersion`-Text, typisierte Versionen, Bestellnummern), gilt: Der
    Writer verwendet die Rohablage nur, solange sie zum normalisierten
    Property passt (aus der Rohablage abgeleiteter Wert == aktueller Wert des
    Properties). Hat der Aufrufer das normalisierte Property nach dem Lesen
    geändert, gewinnt dieses. Je Rohablage ein Test "Property nach dem Lesen
    geändert → Ausgabe folgt dem Property".
14. **Formatspezifische und "nur validiert"-Prüfungen gehören in den Guard.**
    Die Writer erhalten weder Optionen noch das Zielformat, und
    `CanOpenModelValidator` gilt für alle Formate zugleich. Eine Prüfung, die
    nur beim validierten Schreiben greifen oder nur für ein Zielformat gelten
    soll, wird deshalb als Regel im formatbewussten Guard umgesetzt (Hook aus
    WP-09, je Format ein Guard-Delegat), nie im Writer. Die Regeln liegen
    je Formatfamilie in einer eigenen Datei: `Validation/IniWriteRules.cs`
    (EDS, DCF, CPJ) und `Validation/XmlWriteRules.cs` (XDD, XDC); WP-09 legt
    beide an und verdrahtet sie für alle fünf Formate. Spätere WPs ergänzen
    nur noch Regeln in der passenden Datei: INI-Regeln kommen aus der
    INI-Kette, XML-Regeln aus der XDD-Kette, damit sich die Ketten nicht
    über eine gemeinsame Datei blockieren. Jedes WP mit einer solchen
    Prüfung führt die Regeldatei in seiner Dateiliste und testet über die
    kanonische API: validiert wird abgelehnt bzw. gemeldet, unvalidiert
    bleibt das Verhalten unverändert, das jeweils andere Format ist nicht
    betroffen. Dieselbe Trennung gilt für Meldungen beim **Lesen**: was nur
    für ein Format ungültig ist, meldet der jeweilige Reader, nicht der
    gemeinsame `CanOpenModelValidator`.
15. **Gelesene Schreibweise bewahren, wo die Umwandlung gültige Information
    verliert.** Überführt der XDD/XDC-Reader einen Attributwert in eine
    Modell-Darstellung, die weniger tragen kann, hält er die gelesene
    Schreibweise zusätzlich **intern** fest (kein öffentliches Property, von
    `ModelCloner` mitkopiert). Der XDD/XDC-Writer gibt sie unverändert aus,
    solange der daraus abgeleitete Wert dem aktuellen Modell-Property
    entspricht; sonst formatiert er das Property neu (Regel 13). Das betrifft
    Werte, bei denen die Spezifikation die Zusatzinformation zulässt:
    `xsd:date` und `xsd:time` mit Zeitzone, `xsd:hexBinary` ohne festgelegte
    Stellenzahl (`addressOffset`). Attribute mit von der Spezifikation
    festgelegter Stellenzahl (`index`, `subIndex`, `dataType`, `objFlags`)
    werden kanonisch geschrieben.

#### WP-02 · X7 `uniqueIDRef` auf ApplicationProcess auflösen — Stufe A (Fable · high) · L

- **Befund:** `CANopenObject`/`CANopenSubObject` mit `uniqueIDRef` erhalten
  weder DataType, AccessType noch DefaultValue; `ApplicationProcess` wird
  geparst, aber nicht referenziert. `basicDevice.xdd` (343 Referenzen) → EDS mit
  `DataType=0x0`.
- **Spec:** CiA 311 v1.1.0 § 6.5.2.3.2.1 Tab. 48/49 ("shall be defined by the
  referenced element in the application process part"); § 6.4 ApplicationProcess
  (`parameter` mit `dataType`/`dataTypeIDRef`, `access`, `defaultValue`,
  `allowedValues`).
- **Aufgabe:**
  1. Repro-Test mit einem Minimal-XDD (ein Objekt mit `uniqueIDRef`, ein
     `parameter` mit `uniqueID`) und Corpus-Assertion für `basicDevice.xdd`
     (1018sub1 → `DataType=0x0007`, `AccessType=ro`).
  2. Im XDD-Reader nach dem Parsen des `ApplicationProcess` eine Auflösung
     durchführen: `uniqueIDRef` → `ApParameter`; daraus DataType (inkl.
     `dataTypeIDRef` → `ApDataTypes`), AccessType (vollständige Abbildung
     der sieben Schemawerte von `parameter/@access`, siehe unten),
     DefaultValue, Low/HighLimit aus `allowedValues`
     (sofern eindeutig als Range), ParameterName aus `label` nur, wenn das
     Objekt keinen `name` hat.
     Abbildung von `access` auf `AccessType`:

     | `parameter/@access` | `AccessType` | EDS/DCF |
     |---|---|---|
     | `const` | `Constant` | `const` |
     | `read` (Schema-Default) | `ReadOnly` | `ro` |
     | `write` | `WriteOnly` | `wo` |
     | `readWrite` | `ReadWrite` | `rw` |
     | `readWriteInput` | `ReadWriteInput` | `rwr` |
     | `readWriteOutput` | `ReadWriteOutput` | `rww` |
     | `noAccess` | nicht darstellbar | – |

     Die Richtungswerte dürfen nicht auf `rw` zusammenfallen; das Modell und
     der EDS-Writer unterscheiden sie bereits. `noAccess` hat in CiA 306 keine
     Entsprechung: der Zugriffstyp wird dann **nicht** aus der Referenz
     übernommen (ein eigenes `accessType`-Attribut am Objekt gilt weiter,
     sonst bleibt der bisherige Wert), und der Reader meldet eine
     `ParseDiagnostic`. Das ist auch im Strict-Modus nur eine Meldung, keine
     Exception, weil die Eingabe gültig ist. Für XDD→XDD geht nichts
     verloren, weil `uniqueIDRef` und der `ApplicationProcess` erhalten
     bleiben. Tests für alle sieben Werte.
  3. Explizite Attribute am Objekt gewinnen gegenüber der Referenz
     (Spec-Reihenfolge prüfen und im XML-Doc-Kommentar festhalten).
  4. Nicht auflösbare Referenz → `ParseDiagnostic` (lenient) bzw. Exception
     (strict).
  5. **Referenz bewahren:** `CanOpenObject`/`CanOpenSubObject` erhalten ein
     additives Property `UniqueIdRef` (`string?`); heute hat das Modell dafür
     kein Feld, die Zuordnung zum `ApplicationProcess`-Parameter geht beim
     Schreiben verloren. Der XDD/XDC-Writer emittiert `uniqueIDRef` wieder,
     solange der referenzierte Parameter im `ApplicationProcess` des Modells
     existiert. Welche Attribute daneben inline geschrieben werden (nur vom
     Aufrufer gesetzte oder auch die aufgelösten), entscheidet das WP am
     Schema und an Tab. 48/49 und begründet es im PR; Maßstab ist ein
     stabiler XDD→XDD-Round-Trip des Corpus ohne Verlust der Referenzen. Die
     EDS/DCF-Konvertierung nutzt die aufgelösten Werte.
- **Akzeptanz:** Modell-Snapshot aus WP-01 zeigt gesetzte Typen; EDS-Konvertierung
  von `basicDevice.xdd` enthält keinen `DataType=0x0` mehr für referenzierte
  Objekte; Round-Trip XDD→XDD stabil; Diagnostics-Snapshot dokumentiert
  ungelöste Referenzen.
- **Dateien:** `Parsers/XddCommNetProfileParser.cs`,
  `Parsers/XddApplicationProcessParser.cs`, `Parsers/XddReader.cs`,
  `Models/ObjectDictionary.cs` (`CanOpenObject`, `CanOpenSubObject`:
  Property `UniqueIdRef`), `Writers/XddWriter.cs` (246–340:
  `BuildObjectList` und die Objekt-/Subobjekt-Erzeugung, dort wird
  `uniqueIDRef` wieder ausgegeben), `ModelCloner`,
  ggf. neue interne Klasse `Parsers/XddUniqueIdResolver.cs`, Tests unter
  `tests/EdsDcfNet.Tests/Parsers/XddReaderTests.cs` (neue Datei
  `XddUniqueIdRefTests.cs` bevorzugt, siehe T4).
- **Branch:** `feat/xdd-resolve-unique-id-ref` · Commit: `feat(xdd): resolve uniqueIDRef against application process parameters and keep the reference`
- **API:** additiv: neues Property `UniqueIdRef`, deshalb `feat` (Regel 2).
  Abhängig von WP-01 und V1; wegen `XddWriter.cs` zusätzlich erst nach WP-14.

#### WP-03 · S7 Modul-Sektionen `[MxSubExtends]`, `[MxSubExtxxxx]`, `[MxComments]`, `[MxFixedxxxx]` — Stufe A · L

- **Spec:** CiA 306-1 v1.4.0 § 8.3 Tab. 15–17 (`Count`, `ObjExtend`, Zeilen
  `Line<n>`, `Lines`).
- **Aufgabe:** Repro-Round-Trip-Test mit allen vier Sektionstypen; Parser
  füllt `ModuleInfo.SubExtends`, `SubExtensionDefinitions`,
  `FixedObjectDefinitions`, `Comments`; Writer emittiert sie in Spec-Reihenfolge;
  Validator prüft `Count` gegen tatsächliche Einträge. `AdditionalSections`

    vier Modul-Sektionstypen, der bereits in der kanonischen Form des Writers
    vorliegt (normative Sektionsnamen, Writer-Reihenfolge).
  - Modell-Snapshot zeigt gefüllte Modul-Collections.
- **Dateien:** `Parsers/CanOpenReaderBase.cs` (706–727),
  `Parsers/CanOpenSectionParsers.cs` (117–140), `Writers/IniWriterBase.cs`

- **Branch:** `fix/eds-module-sections-roundtrip` · Commit: `fix(eds): parse and write MxSubExtends, MxSubExt, MxComments and MxFixed sections`
- **API:** additiv; bestehende Modell-Properties ggf. nur befüllen.

#### WP-04 · S4 `PPOffsetX=[offset], [address difference]` — Stufe B · M

- **Befund:** `PPOffset1=0, 1` (Spec-Beispiel) wirft `EdsParseException`,
  auch lenient.
- **Spec:** CiA 306-3 v1.2.0 § 5.2.2 Tab. 2, Fig. 2/3.
- **Aufgabe (nach E2):** neues Property `PPOffsetAddressDifference` (`uint?`)
  auf `DynamicChannelSegment`; Parser akzeptiert `a` und `a, b` (Trim,

#### WP-13 · L7 Reihenfolge von `AdditionalSections` — Stufe B · M

- **Befund:** Zusatzsektionen werden alphabetisch und am Dateiende

  2. Alle übrigen Einträge folgen danach in Aufzählungsreihenfolge des
     Dictionary (ohne Zusicherung über diese hinaus).

     ursprünglichen Reader-Position, nicht am Ende; das ist nicht von einem
     unveränderten Eintrag zu unterscheiden und wird so dokumentiert.

#### WP-18 · X2 `objFlags` als hexBinary — Stufe B · S

- **Aufgabe:** Reader parst `objFlags` ausschließlich als hex (XSD:
  `hexBinary`), Writer schreibt vier Stellen (`X4`). Kein Dezimal-Fallback:
  frühere Ausgaben der eigenen Bibliothek (`objFlags="3"`) bleiben lesbar,
  weil einstellige Werte hex und dezimal identisch sind; ungerade Stellenzahl
  wird lenient mit Diagnostic akzeptiert.
- **Dateien:** `Parsers/XddCommNetProfileParser.cs` (122–129), `Writers/XddWriter.cs` (297–299),
  `Validation/XmlWriteRules.cs`.
- **Altbestand:** Der heutige Writer gibt `ObjFlags` dezimal aus, der Reader
  liest dezimal. Für spec-konforme Werte ist das folgenlos: CiA 311
  definiert Bit 0, 1 und 2 (Bit 2: "change of value takes effect after
  reset") und reserviert Bit 3..31; gültig sind also 0–7, und einstellige
  Werte sind dezimal und hex identisch. Mehrstellige Altwerte entstehen nur
  bei gesetzten reservierten Bits; `objFlags="10"` würde nach der Umstellung
  als 0x10 gelesen. Deshalb meldet der XDD/XDC-Reader eine `ParseDiagnostic`,
  wenn nach hex-Interpretation reservierte Bits (**3..31**) gesetzt sind,
  mit dem Hinweis auf mögliche Dezimalausgabe aus Versionen vor diesem Fix.
  Kein stiller Bedeutungswechsel. `objFlags="0004"` ist gültig und wird
  weder beim Lesen noch beim validierten XDD/XDC-Schreiben beanstandet; die
  Regel für das validierte Schreiben (Bit 3..31) steht in
  `Validation/XmlWriteRules.cs`. Die abweichende EDS/DCF-Grenze (Bit 2..31
  reserviert) liegt in WP-15.
- **Branch:** `fix/xdd-objflags-hexbinary` · Commit: `fix(xdd): treat objFlags as four-digit hexBinary`

#### WP-19 · X3 `dynamicChannel`-Attribute — Stufe A · M

- **Schema:** `dataType`, `accessType` (`readOnly`, `writeOnly`,
  `readWriteOutput`), `startIndex`, `endIndex`, `maxNumber`
  (`xsd:unsignedInt`) und `addressOffset` (`xsd:hexBinary`) sind required,
  `bitAlignment` (`xsd:unsignedByte`) ist optional. `pDOmappingIndex`
  existiert im Schema nicht.
- **Modell:** `DynamicChannelSegment` hat heute nur `Type`, `Dir`, `Range`
  und `PPOffset`. Additiv kommen `MaxNumber` (`uint?`) und `BitAlignment`
  (`byte?`) hinzu. `addressOffset` wird auf das bestehende `PPOffset`
  abgebildet; das WP belegt diese Zuordnung an CiA 311 Tab. 51 und CiA 306-3
  § 5.2.2 und hält sie im XML-Doc fest (Bezug zu `PPOffsetAddressDifference`
  aus WP-04 klären).
- **`hexBinary` verlustfrei:** `addressOffset` ist `xsd:hexBinary` ohne
  feste Länge. Im Wertebereich von `hexBinary` zählt die Anzahl der Bytes:
  `0010` (zwei Bytes) und `10` (ein Byte) sind verschiedene Werte, und eine
  ungerade Stellenzahl ist ungültig. Ein `uint` kann die Schreibweise nicht
  tragen. Deshalb:
  - Der Reader hält die gelesene Schreibweise von `addressOffset` intern
    fest (Regel 15; keine öffentliche API, von `ModelCloner` mitkopiert). Der Writer
    gibt sie unverändert aus, solange ihr Zahlenwert dem aktuellen `PPOffset`
    entspricht (Regel 13); sonst formatiert er `PPOffset` neu.
  - Neu formatiert wird immer mit **gerader** Stellenzahl, Großbuchstaben
    und mindestens vier Stellen; eine gemeinsame Hilfsfunktion in
    `XddFormatHelper` stellt das für alle `hexBinary`-Attribute sicher, die
    der Writer aus Zahlen erzeugt.
  - Ein gelesener Wert, der nicht in `uint` passt, wird lenient mit
    Diagnostic gemeldet und über die bewahrte Schreibweise unverändert
    zurückgeschrieben; strict wirft.
  - `dataType` am `dynamicChannel` hat laut Tab. 51 zwei Hex-Stellen
    (anders als am `CANopenObject`); das WP prüft die heutige Ausgabe von
    `FormatDataType` dagegen.
- **Reader:** alle sieben Attribute lesen und speichern, auch ein
  `maxNumber`, das kleiner ist als der Indexbereich. `accessType` in den
  drei Schemawerten (strict), zusätzlich lenient die bisherigen Kurzformen.
  **`pDOmappingIndex` bleibt als Alt-Eingabe lesbar:** frühere Versionen
  dieser Bibliothek haben `PPOffset` in dieses Attribut geschrieben. Es wird
  weiter nach `PPOffset` übernommen, wenn `addressOffset` fehlt, lenient mit
  einer `ParseDiagnostic` ("legacy attribute"), strict mit Exception.
- **Writer:** gespeicherte Werte unverändert ausgeben; `pDOmappingIndex`
  nicht mehr schreiben. Fehlt `MaxNumber` (Modell stammt aus EDS/DCF), wird
  es aus dem Indexbereich abgeleitet und das im XML-Doc genannt; ein
  gelesener Wert wird nie überschrieben.
- **Akzeptanz:** XDD mit `maxNumber` kleiner als der Bereich, mit
  `addressOffset` und `bitAlignment` übersteht XDD→XDD unverändert, auch mit
  `addressOffset="0010"` und `addressOffset="00000010"` (Stellenzahl bleibt
  erhalten); nach Änderung von `PPOffset` im Modell erscheint der neue Wert
  mit gerader Stellenzahl; eine von
  einer älteren Bibliotheksversion erzeugte Datei mit `pDOmappingIndex`
  behält ihren Offset und wird beim Schreiben auf `addressOffset`
  umgestellt; EDS→XDD ist schemagültig; Mapping zwischen EDS-
  `DynamicChannels` und XDD dokumentiert.

  `Parsers/XddCommNetProfileParser.cs` (417–449), `Writers/XddFormatHelper.cs`,
  `Models/DynamicChannels.cs`.

#### WP-20 · X6/X10 Pflichtattribute und Zeitformat — Stufe B · M

- **X6:** `deviceCommissioning` mit `nodeName`, `actualBaudRate`,
  `networkName` immer schreiben. Alle drei sind im Schema `xsd:string`,
  `use="required"`; ein leerer String ist also schemagültig, das Auslassen
  nicht. `actualBaudRate` bei `Baudrate > 0` wie bisher als `"<n> Kbps"`. Bei
  `Baudrate == 0` leerer String plus Validation-Issue im Validated-Modus
  ("Baudrate nicht gesetzt"), weil der Wert fachlich nichts aussagt.
- **X10 Dateiattribute, vollständig für die Gruppe `ag_formatAndFile`:**
  Heute lässt `XddProfileBuilder.AddFileInfoAttributes` jedes leere Attribut
  weg, auch die Pflichtattribute, und `XddFormatHelper.ConvertEdsDateToXsd`
  stellt nur datumsförmigen Text um und gibt alles andere unverändert
  zurück (`02-30-2026` wird zu `2026-30-02`, `banana` bleibt `banana`). Die
  Gruppe wird deshalb als Ganzes geregelt:

  | Attribut | Schema | Schreiben | Validated-Modus (XDD/XDC-Guard) |
  |---|---|---|---|
  | `fileName` | `xsd:string`, required | immer, auch leer | leer → Meldung |
  | `fileCreator` | `xsd:string`, required | immer, auch leer | leer → Meldung |
  | `fileVersion` | `xsd:string`, required | immer (siehe WP-21) | – |
  | `fileCreationDate` | `xsd:date`, required | nur bei gültigem Datum | fehlt oder ungültig → Fehler |
  | `fileCreationTime` | `xsd:time`, optional | nur bei gültigem Wert | vorhanden, aber ungültig → Fehler |
  | `fileModificationDate` | `xsd:date`, optional | nur bei gültigem Datum | vorhanden, aber ungültig → Fehler |
  | `fileModificationTime` | `xsd:time`, optional | nur bei gültigem Wert | vorhanden, aber ungültig → Fehler |
  | `fileModifiedBy` | `xsd:string`, optional | wenn nicht leer | – |

  - "Gültiges Datum" heißt: als Kalenderdatum prüfbar (Monat 1–12, Tag passend
    zum Monat, Schaltjahr), nicht nur der Form nach. Die Umwandlung wird
    dafür auf eine prüfende Variante umgestellt, die bei ungültiger Eingabe
    kein Attribut liefert.
  - **Zeitzone am Datum:** `xsd:date` erlaubt eine Zeitzone
    (`2026-01-01+05:30`, `2026-01-01Z`). Der Reader übernimmt für das
    EDS-Format `MM-DD-YYYY` nur die ersten zehn Zeichen; die Zeitzone ginge
    bei XDD→XDD verloren. Nach Regel 15 hält der Reader deshalb die gelesene
    Schreibweise beider Datumsattribute intern fest, und der Writer gibt sie
    unverändert aus, solange ihr Kalenderdatum dem Modell-Property
    entspricht. Die Gültigkeitsprüfung akzeptiert die Zeitzone. Test:
    `fileCreationDate="2026-01-01+05:30"` übersteht XDD→XDD zeichengenau;
    nach Änderung von `CreationDate` im Modell erscheint das neue Datum ohne
    die alte Zeitzone.
  - Ein ungültiger Wert wird **nie** als Attribut ausgegeben: ein
    weggelassenes optionales Attribut ist schemagültig, ein falsch
    typisiertes nicht. Ein Datum wird nicht erfunden; fehlt
    `fileCreationDate`, bleibt die unvalidierte Ausgabe nicht schemakonform
    (dokumentiert, Entscheidung E10 und Ziel 1 dieser Phase), die validierte
    wird abgelehnt. Die XML-Doku der XDD/XDC-Write-Methoden nennt das.
  - Leere Pflicht-Strings sind schemagültig und werden geschrieben; die
    Meldung im Validated-Modus weist nur darauf hin.
  - Tests je Attribut über die kanonische API: `02-30-2026`, `banana`, leer
    und ein gültiger Wert, jeweils validiert und unvalidiert; die
    Konformitätstests arbeiten mit vollständigen Metadaten und zusätzlich
    mit einem Default-Modell, das im Validated-Modus abgelehnt wird.
- **X10 Zeitformat (XDD/XDC-Seite), verlustfrei:** `CreationTime` und
  `ModificationTime` sind im Modell Strings. Der XDD-Reader übernimmt
  `xsd:time` heute roh, deshalb übersteht der Corpus-Wert
  `19:31:59.7179280+01:00` XDD→XDD bereits unverändert. Eine Umwandlung
  **beim Lesen** in das minutengenaue EDS-Format `hh:mmAM/PM` würde
  Sekunden, Bruchteile und Zeitzone erst zerstören und ist deshalb nicht
  zulässig. Konvertiert wird **beim Schreiben, je Zielformat**:
  - XDD/XDC-Writer: Wert ist bereits gültiges `xsd:time` → unverändert
    schreiben; Wert im EDS-Format → nach `HH:mm:ss` umwandeln; sonst das
    (optionale) Attribut weglassen und im Validated-Modus ablehnen (siehe
    Tabelle oben).
  - Der Reader bleibt unverändert; das Modell hält den Wert so, wie er
    gelesen wurde. Die XML-Doku von `CreationTime`/`ModificationTime` nennt
    beide möglichen Formen.

#### WP-22 · X8 Round-Trip-Verluste DeviceIdentity/Features — Stufe B · M

- **Versionen:** XDD kennt mehrere typisierte, string-wertige `version`-

  API nicht mehr ohne Kompatibilitätskosten zu korrigieren. Deshalb setzt
  dieses WP `Encoding` auch in `XddWriter` und `XdcWriter` um: Datei- und
  Stream-Ausgabe erfolgen im gewählten Encoding, und die XML-Deklaration
  nennt dasselbe Encoding (heute fest `utf-8`: `XDeclaration` in Zeile 191,
  `XmlWriterSettings.Encoding` in Zeile 434, `File.WriteAllText` mit
  `Utf8NoBom`). `WriteToString` liefert einen String; dort bleibt die
  Deklaration wie heute, und die XML-Doku sagt, dass `Encoding` nur die
  Byte-Ausgabe betrifft. Test: XDD und XDC mit ISO-8859-1 und UTF-16
  schreiben, Deklaration und Bytes stimmen überein, und das Ergebnis lässt
  sich nach WP-37 wieder lesen (Round-Trip-Test dort).
- **`MaxInputSize`-Vertrag beim Puffern (wie WP-37):** Datei-APIs
  begrenzen in Bytes (`ByteLimitingStream`, unverändert). `ReadStream` und
  `ReadStreamAsync` begrenzen heute in **dekodierten Zeichen**
  (`ParseReader(reader, maxInputSize)`). Würde das Limit des Aufrufers auf
  den Rohpuffer angewandt, würden gültige Eingaben neu abgelehnt (N
  Nicht-ASCII-Zeichen in UTF-8 sind mehr als N Bytes); ohne eigene Grenze
  wäre das Puffern unbeschränkt. Deshalb: Rohbyte-Obergrenze = Zeichenlimit
  mal maximale Bytes pro Zeichen der in Frage kommenden Encodings **plus
  größte Präambel (BOM)**, mit Überlaufschutz; danach das eigentliche
  Zeichenlimit auf dem dekodierten Text. Bei gesetzter `Encoding`-Option
  liefert das Encoding selbst beide Werte (`GetMaxByteCount`,
  `GetPreamble`). Zusätzlich ein Grenzfalltest mit UTF-8-BOM. Die Hilfsfunktion dafür wird mit WP-37 geteilt. Regressionstests
  synchron und asynchron: Stream mit genau N Nicht-ASCII-Zeichen wird bei
  Limit N akzeptiert, bei N−1 abgelehnt; ein überlanger Stream bricht ab,
  bevor er vollständig gepuffert ist.
- **Akzeptanz:** Fixture mit Latin-1-`Gerät` liest korrekt, Round-Trip
  bewahrt Zeichen; UTF-8-Fixtures unverändert; Thread-Safety-Tests grün.
- **Dateien:** `Parsers/IniParser.cs` (86–87, 179, 204), `CanOpenFileOptions.cs`,
  `CanOpenWriteOptions.cs`, `Utilities/TextFileIo.cs`, `Writers/XddWriter.cs`
  (30, 191, 430–452), `Writers/XdcWriter.cs`.
- **Durchreichen bis zum Reader/Writer:** `FormatCanOpenOperations`
  reduziert Leseoptionen heute auf `StrictParsing` (per Scope) und
  `MaxInputSize` (Delegat-Parameter); Schreiboptionen dienen nur der
  Validierung, die Write-Delegaten nehmen keine Optionen entgegen. Ohne
  zusätzliche Verdrahtung würde eine gesetzte `Encoding`-Option über
  `CanOpenFile.Eds.ReadFile(..., options)` still ignoriert. Das WP umfasst
  deshalb die Anbindung in der Operationsschicht, bevorzugt als

  der Delegat-Signaturen und der öffentlichen Überladungen), für Lesen und

  (`CanOpenFile.<Format>`), nicht nur über die Reader-Klassen;

#### WP-37 · L2 Encoding im XML-Pfad (XDD/XDC) — Stufe A · M

- **Befund:** `SecureXmlParser.ReadContentFromStreamWithLimit{Async}`
  dekodiert alle Bytes mit einem festen UTF-8-`StreamReader`
  (`Parsers/SecureXmlParser.cs:103-108, 121-126`); `ParseDocument` erhält nur
  noch einen `string` und liest ihn über `StringReader`. Eine XML-Deklaration
  wie `encoding="ISO-8859-1"` oder `windows-1252` kann die Dekodierung damit
  nicht mehr steuern; Umlaute in solchen XDD/XDC werden zu U+FFFD und beim
  Zurückschreiben dauerhaft zerstört.
- **Aufgabe:** Bytes begrenzt lesen (bestehender `ByteLimitingStream`,
  einmal puffern, TOCTOU-sicher) und dem sicheren `XmlReader` als **Stream**
  übergeben, sodass BOM und XML-Deklaration die Dekodierung bestimmen. Alle
  Schutzmechanismen bleiben: `DtdProcessing.Prohibit`, `XmlResolver = null`,
  `MaxCharactersInDocument`, Tiefenlimit 64. `ReadString`-Pfad bleibt
  String-basiert. Deklarierte Encodings, die das Zielframework nicht kennt
  (z. B. `windows-1252` ohne CodePages-Provider), führen zu einer klaren
  Parse-Exception mit Encoding-Namen statt zu stiller Fehldekodierung; keine
  neue Dependency. Eine gesetzte `CanOpenFileOptions.Encoding` (aus WP-31)
  überschreibt die Deklaration.
- **Akzeptanz:** Fixtures XDD und XDC mit `encoding="ISO-8859-1"` und
  `Gerät` lesen korrekt (sync und async, Datei und Stream); UTF-8 mit und ohne
  BOM sowie UTF-16 mit BOM unverändert; Byte-Limit-Tests und Tiefenlimit-Tests
  grün; Round-Trip mit den in WP-31 eingeführten Schreib-Encodings
  (ISO-8859-1, UTF-16): schreiben, lesen, Inhalt identisch.
- **Dateien:** `Parsers/SecureXmlParser.cs`, `Parsers/XddReader.cs`,
  `Parsers/XdcReader.cs`, Tests unter `tests/EdsDcfNet.Tests/Parsers/`.
- **`MaxInputSize`-Vertrag erhalten:** Dokumentiert ist: Datei-APIs
  vergleichen gegen die Dateigröße in Bytes, Stream- und String-APIs gegen
  die Anzahl dekodierter Zeichen. Der Stream-Pfad darf deshalb nicht einfach
  byte-limitiert werden (N Nicht-ASCII-Zeichen in UTF-8 sind mehr als N
  Bytes und würden neu abgelehnt). Beim Puffern gilt eine sichere
  Rohbyte-Obergrenze, das Limit des Aufrufers wird danach auf den dekodierten
  Zeichen durchgesetzt (`XmlReaderSettings.MaxCharactersInDocument`).
  **Obergrenze = N × maximale Bytes pro Zeichen + größte unterstützte
  Präambel**, mit Überlaufschutz (Sättigung bei `long.MaxValue`). Die
  Präambel zählt nicht zu den dekodierten Zeichen, belegt aber Bytes: ein
  UTF-16-Dokument mit genau N Zeichen hat 2·N Bytes plus 2 Bytes BOM, UTF-8
  bis 3·N plus 3, UTF-32 bis 4·N plus 4. Ohne den Zuschlag würde ein
  UTF-32-Dokument an der Grenze abgelehnt, bei sehr kleinem N auch UTF-8.
  Regressionstests: Stream mit genau N Nicht-ASCII-Zeichen wird bei Limit N
  akzeptiert und bei N−1 abgelehnt, jeweils **mit BOM** für UTF-8 und
  UTF-16 und ohne BOM für UTF-8.
- **Branch:** `fix/xml-honor-declared-encoding` · Commit: `fix(xdd): honor BOM and declared encoding when reading XDD/XDC`
- **API:** keine. Nach WP-31 (gemeinsame Option). **Nicht** unabhängig von
  der XDD-Gruppe: WP-37 ändert `XddReader.cs` und `XdcReader.cs` (Aufrufe von
  `SecureXmlParser`), ebenso WP-02 (`XddReader.cs`) und WP-22 (beide). Start

Die frühere Trennung in eine Reader- und eine Writer-Gruppe war nicht
haltbar: WP-03, WP-04, WP-06, WP-10, WP-11 und WP-13 ändern jeweils Reader-
**und** Writer- bzw. Validator-Dateien. Sie laufen deshalb in **einer**
Kette. Gruppenübergreifende Abhängigkeiten stehen in Klammern an dem WP,
das warten muss; der Orchestrator startet ein solches WP erst, wenn **alle**
genannten Vorgänger gemergt sind. Diese Tabelle ist für die Reihenfolge
maßgeblich; "Nach WP-xx"-Angaben in den einzelnen WP-Blöcken nennen nur die
inhaltliche Abhängigkeit. WP-23 hat keinen eigenen Lauf (im PR von WP-30),
WP-38 ist gemergt.

**Prüfregel (maschinell, zuletzt 2026-10-01):** Jedes Paar von WPs, dessen
"Dateien"-Angaben dieselbe Datei nennen, muss durch diese Tabelle direkt
oder transitiv geordnet sein. Die Prüfung liest die Reihenfolge aus der
Tabelle selbst und die Dateien aus den WP-Blöcken; sie ist nach **jeder**
Änderung an einem WP oder an der Tabelle zu wiederholen (das Einfügen von
WP-41 ohne erneute Prüfung hatte eine Lücke zu WP-15 hinterlassen). Wer ein
WP ändert, hält deshalb dessen "Dateien"-Liste vollständig: Verlangt die
Aufgabe ein neues Property, gehört die Modelldatei in die Liste; verlangt
sie eine Ausgabe, die Writer-Datei (bei WP-02 hatten beide gefehlt). Eine
zweite maschinelle Prüfung meldet Dateinamen, die im Text eines WP stehen,
aber nicht in seiner Liste. Von der Prüfung
ausgenommen sind Testdateien (jedes WP legt bevorzugt neue Testdateien an,
statt große bestehende zu ändern) und die im nächsten Absatz genannten
Dateien.

**Nicht serialisierbar: Modellklassen, `ModelCloner`, Code-Konstanten.**
Mehrere WPs aus verschiedenen Ketten fügen Modellen additive Properties
hinzu (WP-02, WP-04, WP-06, WP-13, WP-16, WP-21, WP-22), müssen dafür
`ModelCloner` anpassen (`ModelClonerCompletenessTests`) oder ergänzen
Konstanten in `ParseDiagnosticCodes` bzw. bei den Validation-Issue-Codes.
Das vollständig zu serialisieren hieße, die Parallelität aufzugeben. Dafür
gilt stattdessen:

- Unmittelbar vor dem Öffnen der PR holt der Agent den aktuellen `develop`
  in seinen Branch (Merge, kein Rebase), löst Konflikte und lässt Build und
  Tests erneut laufen.
- Meldet GitHub nach einem zwischenzeitlichen Merge einen Konflikt an einer
  offenen PR, setzt der Orchestrator denselben Agent zur Konfliktlösung an
  (wieder per Merge von `develop`). Ein laufender Agent wird nicht mitten in
  der Arbeit umgesetzt.

**Welle 1 (parallel, sofort nach Freigabe):** WP-01, WP-14, WP-07, WP-12,
WP-24, WP-28, WP-29, WP-34, WP-36, WP-39. WP-14 ist klein und steht vorn,
weil es die `WriteFile`-Blöcke aller fünf Writer ändert, auf denen sowohl
die INI-Kette als auch WP-02 aufsetzen.
**Welle 2:** WP-02 (nach WP-01 und WP-14), WP-09 (nach WP-14), WP-25 (nach
WP-24), WP-30 (nach WP-28).
**Welle 3:** WP-03 (nach WP-09), WP-31 (nach WP-07, WP-09 und WP-02),
WP-26 (nach WP-25).
**Welle 4:** WP-17 und WP-37 (nach WP-31).
**Welle 5 ff.:** gemäß Tabelle.

Innerhalb einer Kette startet der nächste Agent erst nach dem Merge des
Vorgängers von frischem `develop`.
