# Handlungsplan zum Deep Review vom 2026-09-30

Basis: Deep Review von `dborgards/eds-dcf-net @ 86e7295` (v1.14.0), abgelegt
unter [`docs/reviews/2026-09-30-deep-review.md`](reviews/2026-09-30-deep-review.md).
Die Befund-IDs (S7, X7, L3, CI-1, …) verweisen auf dieses Dokument; der Plan ist
so formuliert, dass ein Subagent ein Arbeitspaket auch **ohne** das Review
bearbeiten kann.

Status-Legende: `[ ]` offen · `[~]` in Arbeit · `[R]` PR offen · `[x]` gemergt · `[-]` zurückgestellt

## 0. Arbeitsweise und Tracking

- **Kein Issue pro Befund.** Dieser Plan ist das Arbeitsdokument. Es wird genau
  **ein** Tracking-Issue angelegt (`Deep Review 2026-09-30 – Umsetzungsplan`),
  das auf diese Datei verlinkt und die WP-Liste als Checkliste spiegelt. Jede PR
  referenziert es mit `Refs #<n>` (nicht `Closes`), damit die PR-Beschreibung
  einen stabilen Anker hat und der Release-Notes-Generator nichts Falsches
  schließt.
- **Eigene Issues nur für zurückgestellte Themen** (Abschnitt 6), weil sie
  über diesen Plan hinaus überleben müssen und diskutiert werden sollen.
- **Statuspflege:** Der Orchestrator (Hauptsession) aktualisiert die Status-
  Spalten in Abschnitt 7 gesammelt pro Welle in einer `chore(docs):`-PR.
  Subagents ändern diese Datei **nicht**, um Merge-Konflikte zwischen parallelen
  Branches zu vermeiden.
- **Ablauf pro Arbeitspaket (WP):** Subagent in eigenem Worktree → Branch von
  aktuellem `develop` → Repro-Test (rot) → Fix → Tests grün → PR nach `develop`
  → Bericht an Orchestrator → User merged (regulärer Merge-Commit).

## 1. Verbindliche Regeln für jeden Subagent

Diese Regeln gehen in jeden Agent-Prompt (siehe Vorlage in Abschnitt 5).

1. **Branching** (CLAUDE.md): nie direkt auf `main`/`develop`; Branch
   `fix/…`, `feat/…`, `refactor/…`, `chore/…`, `ci/…`; PR gegen `develop`;
   ein Anliegen pro PR; **keine `Co-Authored-By`-Zeilen** im Commit.
2. **Commit-Konvention** (`.github/copilot-instructions.md` § Commit
   Convention): `fix(scope):` für Verhaltenskorrekturen, `feat(scope):` für
   neue öffentliche API, `chore`/`docs`/`ci`/`refactor`/`test` ohne Release-
   Wirkung. Kein `!` und kein `BREAKING CHANGE:`-Footer ohne ausdrückliche
   Freigabe in Abschnitt 3.
3. **Repro zuerst.** Jeder Fix beginnt mit einem fehlschlagenden Test, der den
   Befund exakt reproduziert (Namensschema `MethodName_Scenario_ExpectedBehavior`,
   AAA, XUnit + AwesomeAssertions). Erst dann der Fix.
4. **Boundary-&-Regression-Matrix** aus `CONTRIBUTING.md` § "Boundary &
   regression test guide" ausfüllen und in die PR-Beschreibung (Template
   `.github/PULL_REQUEST_TEMPLATE.md`) übernehmen, sobald Parser, Writer,
   Validator oder Converter berührt werden.
5. **Öffentliche API nur additiv.** Keine Entfernung/Umbenennung/Typänderung
   öffentlicher Member oder Parameternamen. Vor der PR
   `tools/apicompat-check.sh` ausführen. Neue öffentliche Member brauchen XML-
   Doku (`TreatWarningsAsErrors`). Checkliste `CONTRIBUTING.md` § "Public API
   compatibility checklist" abhaken.
6. **Zwei Zielframeworks:** `netstandard2.0` und `net10.0`. Keine neuen
   Paketabhängigkeiten in `src/EdsDcfNet` (Polyfill 11.4.0 ist vorhanden).
   Kein `Encoding.GetEncoding(1252)` ohne CodePages-Provider – nicht
   verfügbar, siehe WP-31.
7. **Kultur:** ausschließlich `CultureInfo.InvariantCulture` für Parse/Format;
   keine String-Interpolation für Zahlen in Datei-Ausgaben.
8. **Build & Test** (macOS/Linux, nur net10.0 lauffähig; net48-Host läuft nur
   in Windows-CI):

   ```bash
   dotnet build -c Release
   dotnet test tests/EdsDcfNet.Tests -c Release --no-build
   ```

   Corpus-Snapshots (`tests/EdsDcfNet.Tests/Integration/Corpus*`) nur mit
   `UPDATE_CORPUS_SNAPSHOTS=1` erneuern und **jede** Snapshot-Änderung in der
   PR-Beschreibung erklären.
9. **Kein Scope-Creep.** Wer außerhalb seines WP einen Fehler findet, meldet
   ihn im Abschlussbericht, fixt ihn aber nicht.
10. **Konfliktträchtige Dateien** (nur ein WP zur Zeit darf sie ändern; der
    Orchestrator serialisiert, siehe Abschnitt 4):
    `Parsers/CanOpenReaderBase.cs`, `Parsers/CanOpenSectionParsers.cs`,
    `Parsers/IniParser.cs`, `Writers/IniWriterBase.cs`,
    `Validation/CanOpenModelValidator.cs`, `Parsers/XddCommNetProfileParser.cs`,
    `Writers/XddProfileBuilder.cs`, `Writers/XddWriter.cs`,
    `tools/semantic-release-run.sh`, `README.md`.
11. **Abschlussbericht** (an den Orchestrator, nicht an den User): PR-URL,
    Commit-Liste, geänderte öffentliche API (oder "keine"), Snapshot-Diffs,
    ausgefüllte Matrix, offene Fragen, Befunde außerhalb des Scopes.

#### WP-02 · X7 `uniqueIDRef` auf ApplicationProcess auflösen — Stufe A (Fable · high) · L

- **Befund:** `CANopenObject`/`CANopenSubObject` mit `uniqueIDRef` erhalten
  weder DataType, AccessType noch DefaultValue; `ApplicationProcess` wird
  geparst, aber nicht referenziert. `basicDevice.xdd` (343 Referenzen) → EDS mit
  `DataType=0x0`.
- **Spec:** CiA 311 v1.1.0 § 6.5.2.3.2.1 Tab. 48/49 ("shall be defined by the
  referenced element in the application process part"); § 6.4 ApplicationProcess
  (`parameter` mit `dataType`/`dataTypeIDRef`, `access`, `defaultValue`,
  `allowedValues`).
- **Aufgabe:**
  1. Repro-Test mit einem Minimal-XDD (ein Objekt mit `uniqueIDRef`, ein
     `parameter` mit `uniqueID`) und Corpus-Assertion für `basicDevice.xdd`
     (1018sub1 → `DataType=0x0007`, `AccessType=ro`).
  2. Im XDD-Reader nach dem Parsen des `ApplicationProcess` eine Auflösung
     durchführen: `uniqueIDRef` → `ApParameter`; daraus DataType (inkl.
     `dataTypeIDRef` → `ApDataTypes`), AccessType (`access`-Mapping auf
     `const/ro/wo/rw`), DefaultValue, Low/HighLimit aus `allowedValues`
     (sofern eindeutig als Range), ParameterName aus `label` nur, wenn das
     Objekt keinen `name` hat.
  3. Explizite Attribute am Objekt gewinnen gegenüber der Referenz
     (Spec-Reihenfolge prüfen und im XML-Doc-Kommentar festhalten).
  4. Nicht auflösbare Referenz → `ParseDiagnostic` (lenient) bzw. Exception
     (strict).
  5. Writer: bestehende Werte werden weiterhin inline geschrieben (kein
     Rückweg zu `uniqueIDRef` in diesem WP).
- **Akzeptanz:** Modell-Snapshot aus WP-01 zeigt gesetzte Typen; EDS-Konvertierung
  von `basicDevice.xdd` enthält keinen `DataType=0x0` mehr für referenzierte
  Objekte; Round-Trip XDD→XDD stabil; Diagnostics-Snapshot dokumentiert
  ungelöste Referenzen.
- **Dateien:** `Parsers/XddCommNetProfileParser.cs`,
  `Parsers/XddApplicationProcessParser.cs`, `Parsers/XddReader.cs`,
  ggf. neue interne Klasse `Parsers/XddUniqueIdResolver.cs`, Tests unter
  `tests/EdsDcfNet.Tests/Parsers/XddReaderTests.cs` (neue Datei
  `XddUniqueIdRefTests.cs` bevorzugt, siehe T4).
- **Branch:** `fix/xdd-resolve-unique-id-ref` · Commit: `fix(xdd): resolve uniqueIDRef against application process parameters`
- **API:** additiv (ggf. `ParseDiagnostic`-Code). Abhängig von WP-01, V1.

- **Befund:** `IsKnownSection` behandelt jeden 1–4-stelligen Hex-Namen
  (`[Face]`, `[Bad]`, `[2000]`) als Objektsektion; ist der Index in keiner
  Objektliste, wird die Sektion weder geparst noch bewahrt, 0 Diagnostics.
- **Aufgabe:** Repro (Sektion `[2000]` ohne Listeneintrag; Sektion `[Face]`).
  Spec-konform wird eine nicht gelistete Objektsektion **nicht** als Objekt

  Diagnostic "object section 0x2000 not listed in any object list" gemeldet
  (lenient: Warnung, strict: Exception). Nicht-Objekt-Namen, die zufällig hex
  sind (`[Face]`, `[Bad]`), gehören ebenfalls in `AdditionalSections`.
- **Akzeptanz:** Round-Trip bewahrt beide Fälle; Diagnostics-Snapshots des
  Corpus ändern sich nur additiv (neue Warnungen) – jede erklärt.
- **Dateien:** `Parsers/CanOpenReaderBase.cs` (160–181, 587–605).
- **Branch:** `fix/eds-preserve-unlisted-sections` · Commit: `fix(eds): preserve unlisted object sections and report a diagnostic`

- **Dateien:** `Parsers/IniParser.cs` (249–254, 469–484).

### Phase 2 – Writer-Korrektheit

#### WP-09 · L3 Steuerzeichen/Trennzeichen im Writer — Stufe A · M

- **Befund:** `ParameterName = "Evil\n[FileInfo]\nFileName=pwned.eds"`
  passiert `CanOpenWriteOptions.Validated` und erzeugt beim Wiedereinlesen
  neue Sektionen/Keys; Keys mit `=` werden beim Lesen falsch gespalten.

  unabhängig von der Option: `EdsWriteException` mit klarer Meldung, weil eine
  Datei sonst nie identisch zurückgelesen werden kann. (c) Property-artiger Test:
  für jedes Zeichen aus einer Steuerzeichen-Liste gilt "Write wirft oder
  Read(Write(x)) == x".
- **Dateien:** `Writers/IniWriterBase.cs` (16), `Validation/CanOpenModelValidator.cs`,
  `Writers/EdsWriter.cs`, `DcfWriter.cs`, `CpjWriter.cs`.

## 5. Orchestrierung

### 5.1 Wellen und Konfliktgruppen

Gruppen, die dieselben konfliktträchtigen Dateien berühren, laufen
**sequenziell** (jeder Start von frischem `develop` nach Merge des Vorgängers).
Verschiedene Gruppen laufen **parallel** in eigenen Worktrees.

| Gruppe | Reihenfolge | Dateien |
|---|---|---|
| Reader-INI | WP-03 → WP-05 → WP-06 → WP-08 → WP-11 (Reader-Teil) | `CanOpenReaderBase.cs`, `CanOpenSectionParsers.cs`, `DcfReader.cs` |
| Writer-INI | WP-09 → WP-10 → WP-11 (Writer-Teil) → WP-13 → WP-15 → WP-35 | `IniWriterBase.cs`, `CanOpenModelValidator.cs` |
| XDD | WP-02 → WP-17 → WP-18 → WP-19 → WP-21 → WP-22 → WP-20 | `Xdd*Parser.cs`, `XddProfileBuilder.cs`, `XddWriter.cs`, `XdcWriter.cs` |
| Unabhängig | WP-01, WP-04, WP-07, WP-12, WP-14, WP-16, WP-31, WP-33, WP-36 | eigene Dateien; WP-04 nach WP-06 wegen `CanOpenSectionParsers.cs` |
| CI | WP-24 → WP-26; WP-25, WP-27 parallel | `tools/*`, `.releaserc.json`, `build.yml` |
| Doku | WP-28, WP-29 → WP-30 → WP-32, WP-23, WP-34 | `README.md`, `docs/**`, `.github/copilot-instructions.md` |

**Welle 1 (parallel, sofort nach Freigabe):** WP-01, WP-09, WP-24, WP-25,
WP-28, WP-29, WP-07, WP-12.
**Welle 2:** WP-02 (nach WP-01), WP-03, WP-10, WP-27, WP-30, WP-14, WP-16.
**Welle 3 ff.:** gemäß Gruppenreihenfolge; WP-11 erst, wenn Reader- und
Writer-Gruppe bis dahin gemergt sind.

Nach jedem Merge in `develop` startet der nächste Agent der Gruppe neu (kein
Rebase laufender Agents).

### 5.2 Prompt-Vorlage für Subagents

```text
Du arbeitest im Repository eds-dcf-net (C#, netstandard2.0 + net10.0) in einem
eigenen Worktree auf Basis von origin/develop. Bearbeite ausschließlich
Arbeitspaket <WP-ID> aus docs/plan-2026-09-30.md (Abschnitt unten zitiert).

Regeln (verbindlich): <Abschnitt 1 des Plans einfügen>.
Tracking: PR-Beschreibung beginnt mit "Refs #<Issue>", nutzt
.github/PULL_REQUEST_TEMPLATE.md und enthält die Boundary-&-Regression-Matrix.
Spec-Quellen: docs/cia/<Datei>, Abschnitte <…>. Zitiere die Spec-Stelle im
Test-Kommentar und im PR.

Arbeitspaket:
<WP-Block aus Abschnitt 4 einfügen>

Vorgehen: 1) Repro-Test schreiben und rot sehen. 2) Fix. 3) dotnet build -c
Release && dotnet test tests/EdsDcfNet.Tests -c Release --no-build. 4) Bei
öffentlicher API tools/apicompat-check.sh. 5) Branch pushen, PR nach develop
mit gh öffnen. 6) Abschlussbericht gemäß Regel 11. Nicht mergen. Keine
Änderungen an docs/plan-2026-09-30.md.
```

- Stufe-A-PRs: optional Review-Agent (Rv), dann `/code-review`, dann regulärer
  Merge-Commit.
- Stufe-B/C-PRs: `/code-review` oder Sichtprüfung, regulärer Merge-Commit.
